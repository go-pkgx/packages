# Recipe overrides

Candidate fixes for genuine **upstream-recipe** bugs — not `bk` gaps — applied
to `pkgxdev/pantry` so the factory can validate them before they are proposed
upstream.

## An override says WHAT it changes, not where the lines are

They used to be `git diff` output. A diff is anchored on the text *around* the
change, so it stops applying the moment upstream edits a neighbouring line —
and nothing downstream says so. On 2026-09-24, 3 of 231 had silently stopped,
among them the `-Werror` switch `mozilla.org/nss` needs, whose absence cost two
rebuilds and a duplicate fix for a defect that was already fixed. On 2026-09-27
a patch that `git apply --check` accepted was refused by the builder's own
applier, and merged broken.

An override is now an HCL file naming the key it changes:

```hcl
project = "curl.se"
why     = "This recipe pins openssl to a 1.x line. Our registry holds no 1.x
           bottle, so it dies in the resolver before a compiler runs. openssl
           1.1.1 has been end-of-life since September 2023. Generated by
           ./openssl3; delete this when upstream retargets the pin."

edits = [
  { path = "dependencies[\"openssl.org\"]", set = "^3" },
]
```

`why` is **required**. An override whose reason lives only in a commit message
is one nobody can ever decide to delete.

## Nothing is written to disk

`bk factory` applies an override to the recipe's *document* as the recipe is
read. `package.yml` is never modified, so its comments survive —
`gnu.org/grep` spends thirteen lines explaining why it names itself as a build
dependency — and a re-run needs no fresh clone, because nothing was changed.

That has one consequence worth knowing: **the pantry on disk is no longer the
recipe the factory builds.** Anything that wants the built recipe must go
through `recipefile.LoadOverridden`, as `bk factory`, `bk closure` and
`overlaycheck` do.

## The verbs

Five, and they were measured rather than invented: every one of the 242 diffs
this replaced was applied to a pristine pantry and the resulting documents
compared, and these five reproduce all of them.

| | |
|---|---|
| `set` | assign a value. Maps deep-merge (RFC 7386's merge-patch rule), lists are replaced. |
| `remove` | delete a key. A verb, not a `null` sentinel: omission has to keep meaning "inherit". |
| `append` / `prepend` | add to a list without restating it, the reason Yocto has `:append`. |
| `from` / `to` | substitute a **substring of a value**. Never an index — reorder the base list and an index deletes the wrong element. |

A `set` that replaces a whole list also carries `expect`, the value it believes
it is replacing, and refuses when that is neither there nor the result. It is
RFC 6902's `test`, and it is the one thing a diff did better: overwriting a
list blind can discard somebody else's change in silence.

A substitution must be **idempotent** — its run has to be gone from the result.
Derived without that rule, the cargo fix came out as `"l --"` → `"l --locked --"`,
which still matches inside `install --locked`: 24 operations across 22 projects
compounded on a second pass.

A `merge` block is available for hand-written files, where a recipe fragment
reads better than a list of paths:

```hcl
merge {
  build {
    dependencies = { "gnu.org/patch" = "*" }   # `= { }`, not a block:
  }                                            # a block header takes an identifier
}
```

## Three answers, where a diff had two

`bk overrides` applies every override and says what each one did. "It did not
apply" used to cover two opposite situations; now they are separate:

| | |
|---|---|
| **applied** | the recipe needed it |
| **redundant** | upstream has caught up — **delete the override** |
| **premise gone** | what it edits is not there any more: an error |

The middle one had no equivalent. An override directory only ever grows unless
something tells you which entries have stopped being needed.

## Naming

`overrides/<slug>.hcl`, where `<slug>` is the project with `/` → `-`
(`crates.io/semverator` → `crates.io-semverator.hcl`). Every file here is HCL;
there are no patches left.

**One file per project**, holding every operation that project needs, from
whatever reason. They are read together, applied in the order the file lists,
and argued about together.

## A project upstream does not carry is not an override at all

It is a recipe of ours, and it lives in
[`pantry-overlay`](https://github.com/go-pkgx/pantry-overlay) — which is also
what a consumer resolves over HTTP. `bk factory` reads it from there when the
pantry has no such project, so nothing about it belongs in this directory.

This used to be eight `*-new.patch` files, each duplicating a recipe the
overlay already held: the same thing written twice, once as a diff for the
builder and once as HCL for the consumer. Exactly 8 of the overlay's 183
projects are absent upstream, and they were the same eight (go-pkgx/bk#231).

The two halves still have to agree for everything else, and four projects were
once published, signed and unreachable to every consumer because only the build
half existed. `go run ./overlaycheck` fails a pull request when they disagree,
and gates the half a consumer reads.

## Workflow

1. Reproduce the failure locally and read the real error.
2. Confirm it is a recipe bug — it builds in real pkgx and differs only in the
   recipe — and not a `bk` behaviour gap. Fix `bk` instead if it is.
3. Write `overrides/<slug>.hcl`. Say **why**, and say what would make it
   unnecessary.
4. `go run github.com/go-pkgx/bk/cmd/bk@main overrides --pantry <fresh clone>`
   to see it apply.
5. Validate it builds.
6. Propose the equivalent change upstream; when it lands, `bk overrides` will
   report the override as redundant and it can be deleted.

## Generated: the openssl 1.x pins

134 pantry recipes pin `openssl.org` to a 1.x line that no published bottle
satisfies, so each dies in the resolver before a compiler runs. Regenerate:

    go run ./openssl3          # -n to see what would change

It reads each recipe as a **document** and names every path that pins openssl,
wherever it sits — runtime, build, or either under a platform. The line-based
version it replaced could not see `amp.rs`, which writes an unquoted `1.1` that
YAML reads as a float, and had not reported `zsync.moria.org.uk` at all.

A project can need an override for more than one reason — `apache.org/serf`
also needs a scons fix — and a project's operations live in one file, so the
generator **cannot own a file it shares**. It writes the ones it owns and
checks the ones it does not, saying so when a shared override lacks the pin.

What this does not claim: that those recipes BUILD against openssl 3. It makes
them resolve. A recipe using an API removed in 3.x now fails in the compiler
instead, which is the factory's job to measure, project by project.

## Generated: the cargo lockfiles

`cargo install` without `--locked` ignores the `Cargo.lock` the release ships
and re-resolves every dependency to the newest semver-compatible crate. The
recipe does not change, the source does not change, and the build rots anyway,
on somebody else's release schedule — `crates.io/pqrs` 0.3.2 locks chrono
0.4.38 and cargo picked 0.4.45. `go run ./cargolocked` covers 19 of 20.

The twentieth, `crates.io/pueue`, is excluded with a reason: its lock pins
time 0.3.31, which no longer compiles.

Two of the nineteen could not be covered at all while these were diffs. The
openssl override for `crates.io/zellij` carried

    script: cargo install --path .

as CONTEXT, so rewriting that line stopped the openssl patch applying and the
build died on `no version of openssl.org satisfies "^1.1"` — a message naming
openssl that has nothing to do with openssl. Guarding against it took eighty
lines of hunk-span arithmetic and still cost those two projects. Two logical
overrides address different KEYS and cannot interact that way.

## Converting a diff, if one turns up

`go run ./logicalise` derives the operations from any `*.patch` that modifies a
recipe, writes them out, reads them back, applies them to a pristine recipe and
demands the same document the patch produced — and demands that applying them
twice changes nothing, which is the property 24 operations across 22 projects
failed before go-pkgx/bk#229. It runs in CI, and with nothing to convert it
says so and passes.
